### D-01 · Low · Loan actions reveal a loan's existence and current status outside the executive's module

- **Lens:** D (Functional correctness)
- **Evidence:** `backend/src/modules/loans/loan-operations.service.ts:140-145` (on a failed conditional update, `getNextStatus(existing.status, action)` throws a 409 whose message names the current status) and `backend/src/modules/payments/payments.service.ts:64-70` (404 only when the id doesn't exist, 409 otherwise). Reads use module scoping instead (`findLoanForViewer`, `loan-operations.service.ts:90-96`). In-process: SANCTION `GET /api/v1/loans/<disbursedLoanId>` → 404 `NOT_FOUND`, but SANCTION `POST /api/v1/loans/<disbursedLoanId>/approve` → 409 `{"code":"INVALID_STATUS_TRANSITION","message":"Cannot approve a loan that is DISBURSED"}`. COLLECTION `GET /api/v1/loans/<appliedLoanId>` → 404, `POST /api/v1/loans/<appliedLoanId>/payments` → 409 `LOAN_NOT_DISBURSED` (a random id → 404).
- **Steps to reproduce:** `cd backend && <env> npx tsx audit-tmp-d/d3-state-machine.ts` (copy of `audit/scripts/d3-state-machine.ts`; see the two "SANCTION on a DISBURSED loan" / "COLLECTION on an APPLIED loan" lines), or: create a DISBURSED loan, then call approve on it as SANCTION.
- **Impact:** An executive who has a loan id can learn that it exists and what stage it's in, although the read endpoints hide it ("404, exactly as if it didn't exist, so executives can't browse other stages"). Ids are 24-hex ObjectIds that staff only see for their own module, so the practical exposure is small.
- **Breaks:** CLAUDE.md section 6 "Never leak whether a resource exists to unauthorized users" (partially; the actor has a staff role, so this is defence in depth).
- **Suggested fix:** In `transitionLoan` and `recordPayment`, when the conditional update matches nothing, return 404 if `!canViewLoanInStatus(actor.role, existing.status)` and keep the 409 only for loans the actor may view (for ADMIN, or a race inside the module). Or drop the status from the 409 message for non-admin actors.
- **Duplicate of:** B-04 (same root cause `loan-operations.service.ts:140-145`; D-01 adds the payments variant, `payments.service.ts:64-70` → 409 `LOAN_NOT_DISBURSED`). The two lenses rate it differently (B-04 Info, D-01 Low). It is a recorded, accepted trade-off (`docs/DECISIONS.md:79` #55, `PLAN.md:288`, `docs/API.md:66`) visible only to staff who already pass the role check, so track it once, at Info (or Low if the generic-message fix is taken).
- **Status:** open

### D-02 · Low · A borrower who has since become eligible by age is sent to the salary-slip step, then refused

- **Lens:** D (Functional correctness)
- **Evidence:** `GET /borrower/progress` and the Sales leads re-run the BRE with today's date (`backend/src/modules/borrower/borrower.service.ts:37-39`, `backend/src/modules/dashboard/dashboard.service.ts:67-77`), but the slip upload checks the result stored at the last profile save (`backend/src/modules/uploads/uploads.service.ts:41-48`, `profile?.breResult.isEligible`). In-process with a shifted clock: on 2026-10-09 IST a borrower born 2003-10-10 saves their details → 422 [AGE] (22). On 2026-10-10 IST, with nothing changed: progress → `currentStep: "SALARY_SLIP", isEligible: true` (stored `breResult.isEligible: false`), and `POST /api/v1/borrower/salary-slip` → 409 `{"code":"PROFILE_INCOMPLETE","message":"Complete your personal details and pass the eligibility check first."}`. Re-saving the same details → 200, after which the upload → 201.
- **Steps to reproduce:** `cd backend && <env> npx tsx audit-tmp-d/d5-stale-bre.ts` (copy of `audit/scripts/d5-stale-bre.ts`).
- **Impact:** A borrower who failed only the age rule shortly before their 23rd birthday comes back, is taken to "Upload your salary slip" and gets an error until they open Personal details and save again. Rare and recoverable (the message points to the details page); no wrong data is stored, and apply re-checks the BRE anyway.
- **Breaks:** none (inconsistent wizard state; the PDF only requires the BRE to block ineligible applicants, which it does).
- **Suggested fix:** In `uploadSalarySlip`, evaluate the BRE freshly (`evaluateEligibility(toBreInput(profile), toBusinessDate())`) instead of reading `profile.breResult`, and save the fresh result to the profile when it differs, so the wizard, Sales and the upload agree.
- **Verification (P1):** Confirmed — re-ran `audit/scripts/d5-stale-bre.ts` in-process with the shifted clock: day 1 profile save → 422 [AGE]; day 2, nothing changed: progress `currentStep=SALARY_SLIP isEligible=true` while the stored `breResult.isEligible=false`, and the slip upload → 409 `PROFILE_INCOMPLETE`; after re-saving the same details, PUT 200 and upload 201. (The script's one "FAIL" line is its check for the correct behaviour, so it failing means the bug reproduces.) Code re-read: `borrower.service.ts:37-39` evaluates the BRE fresh, `uploads.service.ts:41-48` reads the stored `profile.breResult.isEligible`. Rare and recoverable: Low is right.
- **Status:** open

### D-03 · Low · Re-seeding deletes any payment whose UTR starts with "SEED", including real payments on non-demo loans

- **Lens:** D (Functional correctness)
- **Evidence:** `backend/src/scripts/seed-borrowers.ts:135-139`: `resetDemoBorrowerData` deletes payments matching `{ loanId: { $in: demoLoanIds } }` **or** `{ utr: { $regex: "^SEED" } }`, with no restriction to demo loans. UTRs are only checked against `/^[A-Z0-9]{6,30}$/` after upper-casing (`backend/src/config/constants.ts:100`, `payments.schema.ts:6`), so staff can record one. In-process: a non-demo DISBURSED loan, COLLECTION `POST /api/v1/loans/<id>/payments {"utr":"seed12345678","amount":1000000,...}` → 201 (`utr` stored as `SEED12345678`); then `seedDemoData()` → the payment is gone (0 payments on the loan) while the loan keeps `totalPaid=1000000`; ADMIN `GET /loans/<id>` → `totalPaid=1000000, outstanding=9295890`, `GET /loans/<id>/payments` → 0 items.
- **Steps to reproduce:** `cd backend && <env> npx tsx audit-tmp-d/d7-seed.ts` (copy: `audit/scripts/d7-seed.ts`, section 4, the "EDGE: … SEED… UTR survives a re-seed" line).
- **Impact:** After a re-seed (DEPLOYMENT.md tells the operator to re-seed production before submission and again after the E2E run), a real payment record whose UTR happens to start with SEED disappears: `totalPaid` no longer equals the sum of the payments, the payment history loses an entry, and its UTR becomes reusable. Needs both an operator re-seed and a UTR with that prefix on a non-demo loan, so it's unlikely, but it contradicts the README ("safe to re-run … never touches other users", `README.md:236`) and DEPLOYMENT.md:187.
- **Breaks:** the documented re-seed guarantee (`README.md:236`, `docs/DEPLOYMENT.md:187`) and the data invariant `totalPaid == sum(payments)` that the payment service otherwise keeps.
- **Suggested fix:** Drop the `utr` regex branch and delete only payments on the demo loans, plus orphaned seed payments whose `loanId` no longer exists in `loans` (for example `utr ^SEED` **and** `loanId` not in the existing loan ids). Or generate seed UTRs that can't collide with real ones and match on `recordedBy` + demo loan ids.
- **Verification (P1):** Confirmed — in-process (`audit/scripts/v-d03-d04.ts`): after `seedDemoData()`, COLLECTION records `{"utr":"seed12345678","amount":1000000}` on a non-demo DISBURSED loan → 201 (stored as `SEED12345678`); a second `seedDemoData()` leaves 0 payments on that loan while `totalPaid` stays 1000000. Re-read `seed-borrowers.ts:135-139`: the `$or` includes `{ utr: { $regex: "^SEED" } }` with no loan restriction. Needs an operator re-seed plus a colliding UTR: Low is right.
- **Status:** open

### D-04 · Low · seedTestData isn't atomic: a real payment with a TEST-pattern UTR makes it fail halfway and leave inconsistent test loans

- **Lens:** D (Functional correctness)
- **Evidence:** `backend/src/scripts/test-data/test-data-seed.ts:182-184` inserts profiles, then loans, then payments with three separate `insertMany` calls and no transaction; the payment UTRs are fixed (`TEST00000001`…, line 133) and the pre-clean (line 175) only removes payments on the test users' own loans. **D2. Loan math** (script: `audit/scripts/d2-loan-math.ts`)

- Formula matches the PDF exactly: `SI = (P × R × T) / (365 × 100)`, `Total = P + SI`, R = 12, T in days (`backend/src/utils/loan-math.ts:27-30`, mirrored in `frontend/src/lib/loan-math.ts:19-22`); P is in paise so SI comes out in paise, rounded with `Math.round`.
- Worked example: ₹1,00,000 for 90 days → SI 295,890 paise, total 10,295,890 paise; formatted `₹2,958.90` / `₹1,02,958.90` by both the frontend `formatInr` and the backend `formatRupees`. Same values from `POST /borrower/loans`.
- Backend == frontend == an exact BigInt half-up reference on the whole slider grid (₹1,000 steps × every tenure 30–365, 151,536 combos) and on 200,000 random whole-rupee combos: 0 mismatches. An exact .5-paise tie can't happen with R = 12 (12·P·T ≡ 18250 mod 36500 has no integer solution), so the rounding mode never changes a result; the largest numerator (≈2.2×10¹¹) is exact in a double.
- API: 4 boundary combos (₹50,000/₹5,00,000 × 30/365 days) and 20 random combos → 201 with `simpleInterest`/`totalRepayment` equal to both quote functions, `status=APPLIED`, `annualInterestRate=12`, `totalPaid=0`, `outstanding=total`.
- API rejections (400): ₹49,999; ₹5,00,001; 5,000,050 paise (not whole rupees); 10,000,000.5; tenure 29, 366, 90.5; principal as a string; a negative principal; client-sent `totalRepayment`; client-sent `annualInterestRate` (strict schema). The same borrower can still apply afterwards.

**D3. State machine** (script: `audit/scripts/d3-state-machine.ts`)

- Every action × every status through the API, once with the action's own role and once with ADMIN (50 cells): APPROVE/REJECT succeed only on APPLIED (200 → SANCTIONED/REJECTED), DISBURSE only on SANCTIONED (200 → DISBURSED), a payment only on DISBURSED (201; a full payment → CLOSED). Every other cell → 409 (`INVALID_STATUS_TRANSITION` for loan actions, `LOAN_NOT_DISBURSED` for payments) and the loan's status, history length and `totalPaid` are unchanged. No action returns 404 because of module scoping (see D-01); a non-existent id → 404.
- Each successful transition appends one history entry with the right `from`/`to`, `by` = the actor's id and `byRole` = the actor's role (SANCTION/DISBURSEMENT/COLLECTION or ADMIN). A CLOSED loan's history is `null→APPLIED@BORROWER, APPLIED→SANCTIONED@SANCTION, SANCTIONED→DISBURSED@DISBURSEMENT, DISBURSED→CLOSED@COLLECTION`, with `disbursedAt`, `disbursedBy` and `closedAt` set.
- AUTO_CLOSE can't be triggered directly: `POST /loans/:id/close`, `/auto-close` and `/status` → 404. Reject trims and stores the reason (`rejectionReason` + history note); reject without a reason → 400. Wrong-module roles on approve → 403.
- Races: concurrent approve + reject on one APPLIED loan → one 200, one 409, one history entry; concurrent double disburse → one 200, one 409.

**D4. Payments and auto-close** (script: `audit/scripts/d4-payments.ts`)

- Partial payments of 3,000,000 + 2,500,050 + 1 paise → 201 each; `totalPaid` and `outstanding` correct after each, still DISBURSED. Overpaying by 1 paisa → 422 `PAYMENT_RULES_FAILED` [`AMOUNT_EXCEEDS_OUTSTANDING`] ("…outstanding balance of ₹47,958.39."), nothing recorded. The exact remainder → 201, `status=CLOSED`, `outstanding=0`, `closedAt` set, history entry `DISBURSED→CLOSED` byRole COLLECTION, note "Auto-closed: fully repaid"; `totalPaid == sum(payments) == totalRepayment`. A payment on the CLOSED loan → 409 `LOAN_NOT_DISBURSED`.
- Duplicate UTR rollback: a duplicate whose amount would have closed the loan → 409 `DUPLICATE_UTR`, and the payment count, `totalPaid`, status (DISBURSED), history and `closedAt` are all unchanged (the insert and the loan update share one transaction, `payments.service.ts:63-106`). `"  duputr0001 "` → 409 (normalized); the same UTR on another loan → 409 with nothing recorded there.
- Validation: amount 0 / negative / fractional / string, a short or symbol UTR, a non-ISO or missing date → 400; a future date or a date before disbursal → 422. None of them recorded anything.
- Concurrency: two simultaneous full payments → one 201, one 409 `LOAN_NOT_DISBURSED`, one payment, CLOSED. Ten simultaneous 30% payments → exactly 3 × 201 and 7 × 422, `totalPaid` = sum of the 3 payments ≤ total. The same new UTR on two loans at once → one 201, one 409; only one loan changed.
- Invariant over every loan in the run: `totalPaid == sum(payments) ≤ totalRepayment`, and CLOSED ⇔ fully paid with `closedAt`.
- After auto-close, COLLECTION can no longer read the loan or its payments (404, module scoping); the UI expects this and returns to the queue with a toast (`frontend/src/components/dashboard/CollectionModule.tsx:209-212`). ADMIN can list all 4 payments.
