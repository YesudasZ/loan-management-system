# Findings: Lens B: API and RBAC

Format and severity scale: `audit/README.md`.

## Findings

### B-01 · Low · docs/API.md endpoint table is split by blank lines, so 13 of the 25 endpoint rows don't render as a table

- **Lens:** B (API and RBAC)
- **Evidence:** `docs/API.md:50` and `docs/API.md:59` are empty lines inside the endpoint table. In GitHub-flavoured Markdown a blank line ends a table, and the following `| GET | /api/v1/loans | … |` lines have no header/delimiter row, so rows `docs/API.md:51-58` (all `/loans/*` and payment routes) and `:60-64` (leads, dashboard summary, the three `/admin/users` routes) render as plain paragraphs full of pipes.
- **Steps to reproduce:** `awk 'NR>=48 && NR<=61 {print NR": ["substr($0,1,50)"]"}' docs/API.md` shows lines 50 and 59 are empty; open `docs/API.md` on GitHub and scroll to the endpoints.
- **Impact:** The "canonical API reference" is hard to read for the evaluator exactly where the staff and admin routes are described.
- **Breaks:** none (docs polish).
- **Suggested fix:** Delete the two blank lines (and re-run prettier so the new rows are padded like the first 12).
- **Status:** open

### B-02 · Low · Unknown query parameters are silently accepted on every non-list route, contrary to docs/API.md and CLAUDE.md §6

- **Lens:** B (API and RBAC)
- **Evidence:** `docs/API.md:11` says "Bodies, params and queries are validated with strict schemas: unknown fields → 400"; CLAUDE.md §6 says "Use zod `.strict()` schemas on every body, query and param". `middleware/validate.ts:4-7` only takes `body` and `params`; only the 5 list controllers parse `req.query` (`loans.controller.ts:22,32`, `payments.controller.ts:18`, `dashboard.controller.ts:8`, `admin.controller.ts:14`). Run in-process (`audit/scripts/b2-query.ts`) with `?unknownField=1&role=ADMIN`:
  `GET /health` 200 · `GET /api/v1/auth/me` 200 · `GET /borrower/progress` 200 · `GET /borrower/salary-slip` 200 · `GET /borrower/loans/:id` 200 · `GET /loans/:id` 200 · `GET /loans/:id/salary-slip` 200 · `GET /dashboard/summary` 200, while the 5 list routes return 400 `VALIDATION_ERROR`. The same holds for the POST/PUT/PATCH routes (no query schema at all).
- **Steps to reproduce:** as ADMIN, `GET /api/v1/dashboard/summary?anything=1` → 200.
- **Impact:** None exploitable today: these handlers never read `req.query`. It's a gap between the documented contract and the code, and a future handler that starts reading `req.query` would get it unvalidated.
- **Breaks:** CLAUDE.md §6 "zod `.strict()` schemas on every body, query and param"; `docs/API.md:11`.
- **Suggested fix:** Add `query?: ZodType` to `validate()` (defining an own `query` property as is already done for `params`) and mount `validate({ query: emptyQuerySchema })` (`z.strictObject({})`) on the non-list routes; or narrow the doc sentence to "list queries".
- **Status:** open

### B-03 · Info · The global Origin check runs after the JSON body parser, and validate() checks the body before the params

- **Lens:** B (API and RBAC)
- **Evidence:** `backend/src/app.ts:56-58` mounts `express.json()` and `cookieParser()` before `verifyOrigin()`; PLAN.md:285 lists `verifyOrigin` first. In-process (`audit/scripts/b3-order.ts`): `POST /api/v1/auth/login` with `Origin: https://evil.com` and body `{bad` → **400 `INVALID_JSON`** (not 403 `INVALID_ORIGIN`); the same for SANCTION `POST /loans/:id/approve`. With valid JSON the cross-origin request is 403 `INVALID_ORIGIN` before `authenticate` (anonymous and logged-in alike), so nothing is ever executed. Separately, `middleware/validate.ts:24-33` parses `body` before `params`: ADMIN `POST /api/v1/loans/not-an-id/approve` with `{ "evil": true }` → 400 whose `details` list only the body error (`{"field":"","message":"Unrecognized key: \"evil\""}`), not the invalid id.
- **Steps to reproduce:** run `audit/scripts/b3-order.ts` (copy into `backend/audit-tmp-b/` first, see the header comment there).
- **Impact:** None in practice: a cross-origin attacker can only make the server parse ≤ 100 kb of JSON and learn nothing; the error details are just less complete when both id and body are wrong.
- **Breaks:** none (deviation from the order written in PLAN.md:285 only).
- **Suggested fix:** Optional: move `app.use(verifyOrigin(...))` above `express.json()`; validate params before body (or collect both).
- **Status:** open

### B-04 · Info · Wrong-state action errors tell an executive the current status of a loan they can't read

- **Lens:** B (API and RBAC)
- **Evidence:** `loan-operations.service.ts:140-145` falls back to `getNextStatus(existing.status, action)`, whose message names the status (`loan-state-machine.ts:40-44`). In-process (`audit/scripts/b6-scoping.ts`): DISBURSEMENT `GET /api/v1/loans/<closedLoanId>` → 404 `Loan not found`, but `POST /api/v1/loans/<closedLoanId>/disburse` → 409 `"Cannot disburse a loan that is CLOSED"` (likewise `…that is APPLIED/REJECTED/DISBURSED`; SANCTION approve/reject → `…that is SANCTIONED/DISBURSED/CLOSED`).
- **Steps to reproduce:** as DISBURSEMENT, POST `/disburse` on any non-SANCTIONED loan id.
- **Impact:** Staff who already pass the role check can learn that an id exists and its status, which the read scoping hides. No data beyond the status leaks, and the ids are random ObjectIds. This trade-off is a recorded decision (PLAN.md:288, `docs/API.md:66`), following the brief's 409 requirement.
- **Breaks:** none (accepted deviation from CLAUDE.md §6 "Never leak whether a resource exists to unauthorized users").
- **Suggested fix:** None required. If wanted: return a generic "This loan is not awaiting <action>" message for executives outside the owned status.
- **Status:** open

### B-05 · Low · An admin can change their own role by sending their user id in upper-case hex (CANNOT_CHANGE_OWN_ROLE is a case-sensitive string compare)

- **Lens:** B (API and RBAC)
- **Evidence:** `backend/src/modules/admin/admin.service.ts:79` guards with `if (userId === admin.id)`, a plain string compare against the lower-case id from the session, while `objectIdSchema` accepts either case (`backend/src/utils/schemas.ts:5`, `/^[a-f\d]{24}$/i`) and `UserModel.findById` (`admin.service.ts:82`) finds the same user for the upper-case form. In-process (`audit/scripts/b7-staff.ts`), with a second ADMIN present: ADMIN `PATCH /api/v1/admin/users/<OWN ID IN UPPER CASE>/role` `{ "role": "SALES" }` → **200** `{"success":true,"data":{"user":{"id":"6aca2e9e…","email":"admin@test.dev","role":"SALES",…}}}` and the database role is now `SALES`. The same request with the id as issued (lower case) → 409 `CANNOT_CHANGE_OWN_ROLE`. When this admin is the only one, the upper-case request is still refused, but with 409 `LAST_ADMIN` instead of `CANNOT_CHANGE_OWN_ROLE`, so the system can't be locked out.
- **Steps to reproduce:** 1. Log in as ADMIN; create a second ADMIN with `POST /api/v1/admin/users`. 2. Call `PATCH /api/v1/admin/users/<own id>.toUpperCase()/role` with `{ "role": "SALES" }`. 3. Response 200; `GET /api/v1/auth/me` now reports `SALES`. (Or run `audit/scripts/b7-staff.ts`, steps 2–3.)
- **Impact:** Limited: an admin can only demote themselves (or make themselves a BORROWER), and only while another admin exists, by hand-crafting the request (the UI always sends the id as issued). Nobody gains privileges and the last-admin guard still holds. It is still a bypass of a documented business rule, and the audit trail then shows a self-change that the API says can't happen.
- **Breaks:** `docs/API.md:64` (409 `CANNOT_CHANGE_OWN_ROLE`); the staff-management rule "an admin can't change their own role".
- **Suggested fix:** Compare ObjectIds, not strings: `if (user._id.equals(admin.id))` after the `findById`, or normalise ids once in the schema (`objectIdSchema.transform((id) => id.toLowerCase())`), which also fixes any other string compare of ids. Add an integration test with the upper-case id next to `backend/tests/integration/admin-users.test.ts:161`.
- **Status:** open

### B-06 · Low · Client errors from Express's router and the JSON parser (bad %-encoding in a path, unsupported Content-Encoding or charset, corrupt gzip) return 500 INTERNAL_ERROR instead of 4xx

- **Lens:** B (API and RBAC)
- **Evidence:** `backend/src/middleware/error-handler.ts:16-34` maps only `AppError`, `ZodError` and the two body-parser types `entity.parse.failed` / `entity.too.large`; every other error becomes 500, even when it is an http-error with a 4xx `status` and `expose: true`. Raw requests to the in-process app on an ephemeral 127.0.0.1 port (`audit/scripts/b9-raw.ts`), all answered `500 {"success":false,"error":{"code":"INTERNAL_ERROR","message":"Something went wrong. Please try again later."}}`:
  - anonymous `GET /api/v1/loans/%E0%A4%A` (router error `status 400 "Failed to decode param '%E0%A4%A'"`; it fires while matching the route, so before `authenticate`); the same for `POST /api/v1/loans/%E0%A4%A/approve` and `PATCH /api/v1/admin/users/%ZZ/role`;
  - `POST /api/v1/auth/login` with `Content-Encoding: x-unknown` (body-parser `415 encoding.unsupported`);
  - `POST /api/v1/auth/login` with `Content-Type: application/json; charset=latin1` (body-parser `415 charset.unsupported`);
  - `POST /api/v1/auth/login` with `Content-Encoding: gzip` and a plain body (zlib `400 incorrect header check`).
    A valid gzip body works (401 `INVALID_CREDENTIALS`), and the envelope is right in all cases; only the status and code are wrong. The multipart variant of the same root cause is already C-07, the NUL-in-search one C-05.
- **Steps to reproduce:** `curl -i http://localhost:4000/api/v1/loans/%E0%A4%A` against a local API → 500. Or run `audit/scripts/b9-raw.ts`.
- **Impact:** Anyone, without logging in, can make the API answer 500 and write an error-level `Unhandled error` log line (`error-handler.ts:44-46`) on demand. No data leaks (generic message), but it pollutes error monitoring and contradicts the documented contract (500 = internal error only).
- **Breaks:** `docs/API.md:18-31` (400/415 for client errors, 500 only for internal ones).
- **Suggested fix:** In `toAppError`, before the 500 fallback, map any error with a numeric `status` in 400–499 and `expose === true` (http-errors from the router and body-parser) to an `AppError` with that status: 413 → `PAYLOAD_TOO_LARGE`, 415 → `UNSUPPORTED_MEDIA_TYPE` (new code, documented), other 4xx → `INVALID_REQUEST` or `INVALID_JSON`. Add tests for a bad `%`-escape and an unknown `Content-Encoding`. Fixing this generically also fixes C-07.
- **Status:** open

### B-07 · Low · A database error during authentication is reported as 401 and deletes the session cookie, so a short database outage logs every active user out

- **Lens:** B (API and RBAC)
- **Evidence:** `backend/src/middleware/authenticate.ts:12-21`: `findUserForToken` wraps both the JWT check and the database lookup (`findAuthUserById`) in one `try { … } catch { return null; }`, and `authenticate` then calls `clearAuthCookie(res)` and throws 401 (`:30-35`). In-process (`audit/scripts/b9-extra.ts`), ADMIN with a valid cookie, database disconnected: `GET /api/v1/auth/me` → `401 {"code":"UNAUTHENTICATED","message":"Please log in to continue"}` with `Set-Cookie: lms_token=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; SameSite=Lax`; `GET /api/v1/loans` → the same. `GET /health` correctly says 503 `DATABASE_UNAVAILABLE`. The frontend turns `UNAUTHENTICATED` into a redirect to `/login` (`frontend/src/lib/api-client.ts:161-164`).
- **Steps to reproduce:** log in, stop the database (in-process: `mongoose.disconnect()`), call any protected route with the cookie → 401 + cookie cleared; after the database is back the user is still logged out.
- **Impact:** During an Atlas failover or network blip, every logged-in user who makes a request in that window is silently logged out and sent to the login page (which then fails until the database is back). The outage also never shows up as an error in the logs (only ≥ 500 is logged), and the client gets the wrong status (401 "not logged in" instead of a server error).
- **Breaks:** `docs/API.md:20` (401 = not logged in) and `:30` (500 for internal errors).
- **Suggested fix:** Catch only the token-verification error: `let claims; try { claims = await verifyAuthToken(…) } catch { return null }` and let `findAuthUserById` errors propagate to the error handler (→ 500 `INTERNAL_ERROR`, logged, cookie kept). Add a test that a DB failure in `authenticate` gives 500 and no `Set-Cookie`.
- **Status:** open

### B-08 · High · Open redirect after login: `?next=/.//evil.com` (or `/..//`, `/%2e//`) passes getSafeNextPath and becomes `//evil.com`

- **Lens:** B (API and RBAC)
- **Evidence:** `frontend/src/lib/route-access.ts:110-132`. The raw `next` is checked for a leading `//`, backslashes and control characters (`:112-118`), then parsed with `new URL(next, 'https://x.invalid')` (`:123`), and the function returns the **normalised** `url.pathname` (`:132`). URL parsing removes dot segments, so `/.//evil.com` → pathname `//evil.com`; the origin is still the probe origin (`:127` passes) and `resolveRouteAccess('//evil.com', role)` is `allow` (not under `/apply` or `/dashboard`, `:90-91`). `LoginForm` then calls `router.replace('//evil.com')` (`frontend/src/components/auth/LoginForm.tsx:41`); Next 16.4's app router resolves it with `new URL(href, location.href)` (`node_modules/next/dist/client/components/sequential-router-queue.js:85`), sees a different origin (`app-router-utils.js:25-27`) and does a hard navigation (`router-reducer/reducers/navigate-reducer.js:34-35` → `app-router-state.js:316-325` sets `canonicalUrl: url.href`, `mpaNavigation: true` → `app-router.js:254-261` `location.replace(canonicalUrl)`). Output of `audit/scripts/b10-frontend-rbac.ts` (imports the real `route-access.ts`), identical for BORROWER, SANCTION and ADMIN:
  `"/.//evil.com" → "//evil.com" → https://evil.com/`, `"/..//evil.com" → "//evil.com"`, `"/x/..//evil.com" → "//evil.com"`, `"/apply/..//evil.com" → "//evil.com"`, `"/%2e//evil.com" → "//evil.com"`, `"/%2E%2E//evil.com" → "//evil.com"`.
  The vectors the code was written for are blocked (`//evil.com`, `/\evil.com`, `https://evil.com`, `%2F%2Fevil.com`, `\\evil.com`, a tab, `javascript:` → home; `/%2F%2Fevil.com` stays on-site as a 404 path), and the existing tests only cover those (`route-access.test.ts:119-129`), so `npx vitest run src/lib/route-access.test.ts` is green (28/28).
- **Steps to reproduce:** 1. Logged out, open `https://<frontend>/login?next=/.//evil.com` (local: `http://localhost:3000/login?next=/.//evil.com`). 2. Log in with any demo account. 3. The browser leaves the LMS for `https://evil.com/`. (Not run in a browser here: Lens B may not serve the frontend. The function result is proven by the script; the Next router path is read from the installed `next@16.4.0` source. Phase 2 can confirm in a browser on Lens E's local server.)
- **Impact:** Anyone can send a link to the real LMS login page that, after the victim logs in successfully, lands them on an attacker's site (e.g. a copy of the login page saying "session expired, sign in again" to harvest the password, or a fake "payment details" page for a borrower). No data is read directly and the victim must log in, but it is exploitable with a plain link and it defeats the protection the code says it provides (`route-access.ts:106-109`).
- **Breaks:** The function's own contract ("Blocks open redirects such as `//evil.com`…"); OWASP unvalidated-redirect guidance; this audit's B10 check.
- **Suggested fix:** Validate the value you return, not only the input: after parsing, `const path = url.pathname; if (path.startsWith('//') || path.includes('\\')) return home;` (or reject any `next` whose normalised `pathname + search` differs from the input, or which contains a `.`/`..`/`%2e` segment). Add the six vectors above to `route-access.test.ts`.
- **Status:** open

## B4 · Route × identity matrix (in-process, 304 cells, 0 mismatches)

Script: `audit/scripts/b4-matrix.ts` (supertest against `createApp()` + `MongoMemoryReplSet`). Identities: anonymous, one user per role, `BORROWER` = borrower A, `BORROWER2` = borrower B. Each allowed cell used fresh data in the right state (e.g. SANCTION and ADMIN each approved their own APPLIED loan; DISBURSEMENT reads a SANCTIONED loan, COLLECTION a DISBURSED one; borrowers walk profile → slip → apply → read in order). Denied borrower cells on `/loans/:id…` used the borrower's **own** loan id, so owning the loan never helps. A plain number means expected = actual. Expected values: public routes → their success status for everyone; otherwise 401 anonymous, 403 for a role not in the route's list, and for allowed roles the success status, 404 (rows `a`/`b`: another borrower's loan, a loan outside the executive's module status, or an unknown id) or 400 (rows `c`: malformed id).

The 2xx bodies were checked too: approve → `SANCTIONED`, reject → `REJECTED`, disburse → `DISBURSED`, payment 201 with `amount` 100000, `POST /admin/users` → role `SANCTION`, `PATCH …/role` → `SALES`; `GET /loans` returned only `APPLIED` for SANCTION, only `SANCTIONED` for DISBURSEMENT, only `DISBURSED` for COLLECTION and all statuses for ADMIN.
