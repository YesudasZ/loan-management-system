# Findings: Lens C: Security

Format and severity scale: `audit/README.md`.

## Findings

### C-01 · Info · JWT verification does not require an `exp` claim

- **Lens:** C (Security)
- **Evidence:** `backend/src/utils/jwt.ts:36` calls `jwtVerify(token, key, { algorithms: ['HS256'] })` without `requiredClaims: ['exp']` (or `maxTokenAge`). Local run: a token signed with the real secret but with no `exp` → `GET /api/v1/auth/me` 200.
- **Steps to reproduce:** `npx tsx audit/scripts/c1-auth.ts` (line "token WITHOUT exp signed with the real secret | status=200").
- **Impact:** None while the secret is safe: the server always sets `exp` (1 day) and forging needs the secret. Defence in depth only.
- **Breaks:** none
- **Suggested fix:** `jwtVerify(token, key, { algorithms: [ALGORITHM], requiredClaims: ['exp', 'sub'] })`, optionally `maxTokenAge: JWT_EXPIRY`.
- **Status:** open

### C-02 · Info · Logout does not revoke the JWT (documented trade-off)

- **Lens:** C (Security)
- **Evidence:** `backend/src/modules/auth/auth.controller.ts:20-23` only clears the cookie. Local run: the old token replayed after logout → `GET /auth/me` 200. Already listed in `docs/SECURITY.md` "Known limitations" (stateless JWT, 1-day expiry).
- **Steps to reproduce:** `npx tsx audit/scripts/c1-auth.ts` (line "old JWT replayed after logout").
- **Impact:** A stolen cookie stays usable for up to 24 h after the victim logs out. Mitigated by httpOnly + 1-day expiry + per-request user reload.
- **Breaks:** none (CLAUDE.md only asks for a short expiry and clearing the cookie)
- **Suggested fix:** none needed for submission; future: a `tokenVersion` on the user checked in `authenticate`.
- **Status:** open

### C-03 · Low · The login "dummy hash" is built on first use, not at startup (first unknown-email login is ~2x slower)

- **Lens:** C (Security)
- **Evidence:** `backend/src/modules/auth/auth.service.ts:25-28` (`dummyPasswordHash ??= bcrypt.hash(...)`) runs the extra `bcrypt.hash` inside the first unknown-email login. `docs/DECISIONS.md` #30 says "a startup-made dummy hash". Local timing: first unknown-email login 99 ms; afterwards unknown email median 49.2 ms vs wrong password median 49.2 ms (20 tries each).
- **Steps to reproduce:** `npx tsx audit/scripts/c2-session.ts` (lines "first unknown-email login" and "x20 ms").
- **Impact:** Only the first unknown-email login after each process start (Render free instances restart after idling) is distinguishable, by about one bcrypt hash. Negligible enumeration value; mainly a docs/code mismatch.
- **Breaks:** CLAUDE.md §6 "never reveal whether the email exists" (marginal); `docs/DECISIONS.md` #30 accuracy
- **Suggested fix:** Call `getDummyPasswordHash()` once from `server.ts` after connecting (or at module load), or reword DECISIONS #30.
- **Status:** open

### C-04 · Medium · Rate-limit keying is still unmeasured on the deployed path: either a shared bucket (hops=1) or an XFF spoof bypass (hops=2)

- **Lens:** C (Security)
- **Evidence:** `backend/src/app.ts:38` (`trust proxy` = `TRUST_PROXY_HOPS`), `backend/src/middleware/rate-limit.ts:16-27` (default `req.ip` key). `PROGRESS.md:104` and `:272`, `docs/DEPLOYMENT.md:170`: "`TRUST_PROXY_HOPS` is still `1`", measurement open. Local runs (`audit/scripts/c3-rate-limit.ts`, supertest's socket plays the last proxy):
  - hops=1: `X-Forwarded-For: 198.51.100.<n>, 203.0.113.7` (spoofed first entry rotated) → 429 at the 11th failure: a client can't spoof through one appending proxy.
  - hops=1: `X-Forwarded-For: 198.51.100.<n>, 203.0.113.7, 192.0.2.1` (two proxies, as on browser → Vercel → Render) → 429 at the 11th failure whatever `<n>` is, so every client behind the same last-but-one hop shares ONE bucket.
  - hops=2: the same rotated header with one fixed proxy entry (a client calling `*.onrender.com` directly) → never limited after 30 failures (bypass).
- **Steps to reproduce:** `TRUST_PROXY_HOPS=1 npx tsx audit/scripts/c3-rate-limit.ts`, then again with `TRUST_PROXY_HOPS=2` (same env as the README command).
- **Impact:** If the Vercel → Render path really has one more hop than direct access (likely), the current value 1 makes `req.ip` the Vercel egress address: 10 failed logins or 10 sign-ups from anyone sharing that address lock everybody on it out (429 for 15 min / 1 h), which an evaluator could hit; brute-force protection becomes global, not per attacker. Setting 2 fixes that but lets a direct-to-Render caller rotate a spoofed XFF entry and brute-force logins without limit. Documented in `docs/SECURITY.md` "Known limitations", but unresolved. Escalate to High if the Render log shows `clientIp` is not the real client IP.
- **Breaks:** CLAUDE.md §6 "Rate-limit `/auth/*`" and "`trust proxy` set for Render" (effectiveness)
- **Suggested fix:** Measure now (DEPLOYMENT.md checkpoint B step 5). Then either key the limiter on a header only Vercel can set (e.g. have Vercel's rewrite add a shared-secret header and reject requests without it, or key on `x-vercel-forwarded-for` only when that secret header matches), or block direct access to the Render URL. At minimum set hops to the measured value and record the residual risk.
- **Status:** open

### C-06 · Low · The "details locked during an active loan" rule can be bypassed by racing a profile edit against apply

- **Lens:** C (Security)
- **Evidence:** `backend/src/modules/borrower/borrower.service.ts:59-77` checks `assertNoActiveLoan` and then upserts the profile in a separate step; `backend/src/modules/loans/loans.service.ts:82-131` reads the profile, checks, and creates the loan in separate steps. Locally, `Promise.all([POST /borrower/loans, PUT /borrower/profile {monthlySalary: 100}])` for a ready borrower gave **201 (loan created) and 422 (ineligible profile saved) in 10 of 10 runs**: the borrower ends up with an APPLIED loan while their stored profile was changed after the lock should have applied.
- **Steps to reproduce:** `npx tsx audit/scripts/c8-business-logic.ts` (line "apply racing an ineligible profile edit … 10").
- **Impact:** No privilege or money gain: the loan's `applicant` snapshot is the eligible profile that apply read, and the BRE still ran on it, so staff see consistent data. Only the profile (and Sales/borrower views of it) can drift from the loan, and only by the borrower racing themselves. The related slip-replacement race (a loan pointing at a deleted slip) is already a documented known limitation; it didn't reproduce in 10 local runs.
- **Breaks:** none in the PDF; weakens the documented lock (`borrower.service.ts:56` "Locked while the borrower has an active loan")
- **Suggested fix:** Make the lock atomic, e.g. run apply in a transaction that also writes the profile (bump a `version`/`lockedAt` conditioned on the `updatedAt` it read) and do the profile update in a transaction that re-checks for an active loan, so MongoDB's write conflict serialises the two; or document it next to the slip race.
- **Status:** open

### C-07 · Low · Malformed multipart uploads (no boundary, truncated body, NUL in a part header) return 500 instead of 400

- **Lens:** C (Security)
- **Evidence:** `backend/src/middleware/upload.ts:14-21` (`toUploadError`) maps only `MulterError`; busboy's own parse errors pass through unchanged and end up as 500 `INTERNAL_ERROR` in `backend/src/middleware/error-handler.ts:32`. Local runs (BORROWER cookie, eligible profile, allowed Origin), `POST /api/v1/borrower/salary-slip`:
  - `Content-Type: multipart/form-data` without `boundary=` → 500 (log: `Error: Multipart: Boundary not found`);
  - a valid one-file body cut 30 bytes short → 500 (`Unexpected end of form`);
  - body `this is not multipart at all` with a boundary → 500 (`Unexpected end of form`);
  - a part with `filename="slip\0.pdf"`, `"slip.pdf\0.exe"` or `"slip.exe\0.pdf"` (raw NUL byte) → 500 (`Malformed part header`).
    Every body is the generic `{"code":"INTERNAL_ERROR","message":"Something went wrong. Please try again later."}` (no leak), nothing is stored, and each logs an error-level `Unhandled error` with a stack.
- **Steps to reproduce:** `npx tsx audit/scripts/c9-uploads.ts` (same env as the README command; FAIL lines "filename with NUL", "multipart without boundary", "truncated multipart body", "garbage multipart body").
- **Impact:** Reachable only by a logged-in BORROWER (the parser runs after `authenticate` + `requireRole`), so no anonymous log flooding. A broken client request gets "Something went wrong" instead of the documented 400 `INVALID_UPLOAD`, and error logs/alerts get noise a borrower can generate at will.
- **Breaks:** CLAUDE.md §2/§6 "validate at the boundaries (requests, env, uploads)"; `docs/API.md:20,45` (400 `INVALID_UPLOAD` documented for bad multipart)
- **Suggested fix:** In `uploadSingleFile`, treat every error the multipart parser reports as a client error: keep `LIMIT_FILE_SIZE` → 413, and map any other error (MulterError or not) to `new AppError(400, 'INVALID_UPLOAD', 'The upload could not be read. Send exactly one file in the "file" field.')`. Memory storage can't fail on disk, so the parser's errors are always about the request body. Add a test with a missing boundary and a truncated body.
- **Status:** open

### C-08 · Info · PDF content is not inspected: a PDF with a JavaScript action, or HTML after the `%PDF-` header, is accepted

- **Lens:** C (Security)
- **Evidence:** `backend/src/modules/uploads/salary-slip-file.ts:22-35` checks extension + declared MIME + magic bytes only. Local: `%PDF-1.4\n<html><body><script>alert(document.domain)</script></body></html>\n%%EOF` as `slip.pdf` → 201; a PDF with `/OpenAction << /S /JavaScript /JS (app.alert\(1\)) >>` → 201. - **Steps to reproduce:** `npx tsx audit/scripts/c9-uploads.ts` (INFO lines "PDF magic + HTML/script polyglot" and "PDF with /OpenAction JavaScript").
- **Impact:** None found. PDF JavaScript runs inside the browser's PDF viewer sandbox (Chrome/PDFium, Firefox/pdf.js), not in the app origin, even though the SANCTION viewer frames the slip same-origin through the `/api` rewrite (`frontend/src/components/dashboard/SalarySlipViewer.tsx:22`).
- **Breaks:** none (CLAUDE.md §6 asks for extension + MIME + magic bytes, all present)
- **Suggested fix:** none needed for submission. Keep the per-response CSP and `nosniff` on both slip routes.
- **Status:** open

### C-09 · Low · Body-parser and URL-decoding client errors become 500 (anonymous, before any rate limit)

- **Lens:** C (Security)
- **Evidence:** `backend/src/middleware/error-handler.ts:16-33` recognises only `AppError`, `ZodError` and the body-parser types `entity.parse.failed` / `entity.too.large`; every other error becomes 500 `INTERNAL_ERROR` and an error-level "Unhandled error" log with a stack. Local runs (both `NODE_ENV=test` and `NODE_ENV=production`, no cookie):
  - `POST /api/v1/auth/login` with `Content-Type: application/json` and `Content-Encoding: compress` → 500 (log: `UnsupportedMediaTypeError: unsupported content encoding "compress"`, `status: 415`);
  - the same with `Content-Encoding: gzip` and a plain JSON body → 500 (`incorrect header check`, `status: 400`);
  - `GET /api/v1/loans/%E0%A4%A/salary-slip` (anonymous) → 500 (`URIError: Failed to decode param '%E0%A4%A'`, `status: 400`); the router decodes params before `authenticate` runs.
    Bodies are the generic envelope; no stack or message leaks (checked in production mode).
- **Steps to reproduce:** `NODE_ENV=production … npx tsx audit/scripts/c10-headers.ts` (lines "Content-Encoding" and "malformed percent-encoding"), or e.g. `curl -i -X POST localhost:4000/api/v1/auth/login -H 'Content-Type: application/json' -H 'Content-Encoding: compress' -d '{}'`.
- **Impact:** Anyone can produce unlimited error-level log entries with stacks (`express.json()` runs before the auth rate limiters; the param decode happens before auth) and get a misleading 500 for their own malformed request. No data exposure; Render log noise and false alerts only. Same family as C-05 and C-07.
- **Breaks:** CLAUDE.md §2 "validate at the boundaries" / "one central error handler" (client errors classed as server errors)
- **Suggested fix:** In `toAppError`, before the 500 fallback, map any error that carries a 4xx `status` (http-errors sets `status` + `expose: true`; Express sets `status: 400` on the URIError) to a client-safe AppError, e.g. `new AppError(status, 'BAD_REQUEST', 'The request could not be processed')` (415 → `UNSUPPORTED_MEDIA_TYPE`). Fixing it there also covers C-07 if the multipart errors are given a 400 first. Add tests for an unsupported encoding and a malformed `%` sequence.
- **Status:** open

### C-10 · Low · A database outage logs every user out: `authenticate` treats any lookup error as "not logged in" and clears the cookie

- **Lens:** C (Security)
- **Evidence:** `backend/src/middleware/authenticate.ts:12-21`: `findUserForToken` wraps both the JWT check and the `findAuthUserById` database read in one `try { … } catch { return null; }`, and the caller then clears the cookie and throws 401 (`:31-35`). Local run: after `mongoose.connection.close()`, `GET /api/v1/loans` with a valid ADMIN cookie → 401 `{"code":"UNAUTHENTICATED","message":"Please log in to continue"}` plus `Set-Cookie: lms_token=; …; Expires=Thu, 01 Jan 1970 00:00:00 GMT` and **no log line**; by contrast anonymous `POST /auth/login` → 500 with `MongoNotConnectedError` logged, and `/health` → 503 `DATABASE_UNAVAILABLE`.
- **Steps to reproduce:** `npx tsx audit/scripts/c10-headers.ts` (INFO line "database down, valid ADMIN cookie").
- **Impact:** Fails closed, so no bypass. But during an Atlas outage or a failover longer than the 5 s server-selection timeout, every signed-in user (evaluator included) gets "Please log in", loses the session cookie and must sign in again after recovery. The cause never reaches the Render logs for authenticated traffic, which hides real incidents.
- **Breaks:** CLAUDE.md §2 errors rule ("throw typed AppError … one central error handler"); the swallowed error also contradicts "no try/catch noise"
- **Suggested fix:** Catch only token errors: `let claims; try { claims = await verifyAuthToken(...) } catch { return null; }` and call `findAuthUserById(claims.userId)` outside the `try`, so database errors reach the error handler (500, or map `MongoNotConnectedError`/`MongoServerSelectionError` to 503 `DATABASE_UNAVAILABLE`) without clearing the cookie. Add a test that stubs the user lookup to throw and expects 5xx and no `Set-Cookie`.
- **Status:** open

### C-11 · Low · Env validation accepts the published `.env.example` JWT secret, other trivially weak secrets, and CORS entries that become the origin `"null"`

- **Lens:** C (Security)
- **Evidence:** `backend/src/config/env.ts:31-33` only requires `JWT_SECRET.length >= 32`; `frontend/next.config.ts:9` the same. `env.ts:13-17` keeps whatever `new URL(entry).origin` returns. Local `parseEnv` runs (`audit/scripts/c11-env.ts`), all accepted without error, also with `NODE_ENV=production`:
  - `JWT_SECRET=change-me-to-at-least-32-random-characters` (the exact placeholder committed in `backend/.env.example:13` and `frontend/.env.example:8`), 32 spaces, `"a"` × 32. `next.config.ts` also loads with the placeholder.
  - `CORS_ORIGINS=localhost:3000` (scheme forgotten) or `file:///x` → allowed origins `["null"]`, because WHATWG URL parses `localhost:` as a scheme and serialises the origin as the string `"null"`; `verifyOrigin` and `cors` then accept `Origin: null` (sandboxed iframes, `data:` pages). `CORS_ORIGINS=" , "` → `[]`.
- **Steps to reproduce:** `npx tsx audit/scripts/c11-env.ts` (lines "WEAK ACCEPTED" and "CORS_ORIGINS not a URL"); frontend: `cd frontend && env -i PATH="$PATH" HOME="$HOME" BACKEND_URL=http://localhost:4403 JWT_SECRET=change-me-to-at-least-32-random-characters npx tsx -e "require('./next.config.ts')"` loads without error.
- **Impact:** Only matters if an operator copies a placeholder or makes a typo, but then it fails open silently: with the placeholder secret anyone can sign a valid session for any user id (`authenticate.ts` re-reads the role from the DB, so the attacker becomes whoever owns that id); ObjectIds made in one seed run differ only in a counter, so from one known id (e.g. their own) staff ids are guessable and impersonation, staff included, becomes feasible. With `"null"` allowed, credentialed CORS from opaque origins is permitted (the cookie lives on the Vercel domain, so the practical reach is small). Escalate to Critical if the user finds the deployed `JWT_SECRET` on Render/Vercel is the placeholder (check its length/prefix without printing it).
- **Breaks:** CLAUDE.md §6 "The secret is ≥ 32 random characters" and "Validate all env vars with zod at startup; crash fast if one is … [wrong]"
- **Suggested fix:** In both schemas add `.refine((v) => !/change-me/i.test(v) && new Set(v).size >= 10, 'JWT_SECRET looks like a placeholder; use openssl rand -base64 48')` (or require ≥ 16 distinct characters when `NODE_ENV=production`). In `originListSchema`, reject entries whose origin is `"null"` or whose protocol isn't `http:`/`https:` (and require `https:` in production except `localhost`), and require at least one origin after trimming. Add unit cases to `backend/tests/unit/env.test.ts`.
- **Status:** open
